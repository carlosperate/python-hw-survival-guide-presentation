MicroPython and CircuitPython

MicroPython

A lean Python 3 for microcontrollers, by Damien George.

The most from each chip. machine works on every board, and each port (the build for one chip family) adds modules for what its chip can do.

CircuitPython

Adafruit's fork of MicroPython, for beginners and education.

The same code everywhere. One API on every board; a board that can't support a module leaves it out.

Blinka brings that API and Adafruit's drivers to CPython on single-board computers like the Raspberry Pi.

Something very different: Interrupts

A pin edge or a timer can pause your programme and run an interrupt.


from machine import Pin
presses = 0

def on_press(pin):  # the interrupt handler
    global presses
    presses += 1    # an int: no new object

button = Pin(BUTTON_PIN, Pin.IN, Pin.PULL_UP)
# a press pulls the pin low: a falling edge
button.irq(on_press, Pin.IRQ_FALLING)

Not on CircuitPython: use countio, keypad

  • Soft Interruptdefault for pins: queued, so it can lag. May allocate
  • Hard Interrupthard=True: runs at once, heap locked: no floats or append()

    f runs soft, soon after
  • Be briefyour program waits, no print(), sleep() or filesystem actions

Which lines cost memory?

  • import, def, class
  • a new list, dict, str or bytes
  • s + t, f"{t}", data[4:20]
  • uart.read(64)
  • float maths, even n / 2*
  • if, for, while, try
  • locals, small-int maths: n += 1
  • calling a function or a method
  • reading a pin: pin.value()
  • writing into a buffer: buf[i] = b

Time every call with a decorator

Put @timed above a function, and each call prints how long it took.


import gc, time

def timed(f):
    name = str(f).split()[1]  # portable name
    def wrapper(*args, **kwargs):
        gc.collect()  # no GC mid-timing
        t0 = time.ticks_us()
        result = f(*args, **kwargs)
        dt = time.ticks_diff(time.ticks_us(), t0)
        print(name, dt, "us")
        return result
    return wrapper
  • Time a few calls: the first is often slower.
  • Ticks wrap: use ticks_diff().
  • Not for async: on async def it only times creating the coroutine.
  • CircuitPython: use time.monotonic_ns().

A driver is a small class


from micropython import const
_ID = const(0xD0)
_CTRL = const(0xF4)
_TEMP = const(0xFA)

class BME280:
    def __init__(self, i2c, addr=0x76):
        self.i2c, self.addr = i2c, addr
        self._buf = bytearray(3)
        if i2c.readfrom_mem(addr, _ID, 1) != b"\x60":
            raise OSError("BME280 not found")
        i2c.writeto_mem(addr, _CTRL, b"\x27")  # wake

    def raw_temperature(self):
        b = self._buf
        self.i2c.readfrom_mem_into(self.addr, _TEMP, b)
        return b[0] << 12 | b[1] << 4 | b[2] >> 4
  1. Registers as const()
  2. Take the bus, don't make it: I2C, SoftI2C or a fake one for tests
  3. Check the ID, wake it up
  4. One buffer, reused

Which communication bus?

  • A bus is a set of signals between chips & rules for exchanging data (the protocol).
  • Microcontrollers have built-in hardware for common ones like: UART, I²C and SPI.
  • You rarely choose: the part's datasheet or product page specifies the bus.
  • You still need to know it: it decides which pins you wire, and what bus you hand the driver.

i2c = I2C(0, scl=Pin(5), sda=Pin(4))
bme = bme280.BME280(i2c=i2c)
  • Not every part needs a bus: buttons use a plain pin (GPIO), servos use pulses (PWM), analogue sensors a voltage (ADC).
  • Some buses might not be built into the microcontroller, but can be implemented in software.

UART: no clock, so agree in advance

UART sends bytes one bit at a time from TX to the other end's RX. There is no clock wire, so both ends agree on the speed, the baud rate, in advance.

'A' = 0x41 = 0100 0001 · sent least significant bit (LSB) first

Idle: the line sits HIGH while nothing is sent.

START: the line drops for one bit. The receiver starts timing from this edge.

Eight data bits, least significant first: 'A' goes out backwards.

STOP: back to HIGH for at least one bit, ready for the next byte.

The receiver samples the middle of each bit at its baud rate. Send at 9600, read at 19200: garbage, and no exception.

machine.UART · SparkFun: Serial Communication

SPI: to read, you must write

SPI has a clock, a wire each way and a chip-select (CS) per device. Every tick moves one bit each way.

cs(0); spi.write_readinto(b'\xD0\x00', buf); cs(1) → buf[1] == 0x60

Idle: CS is HIGH, so the sensor ignores the bus.

cs(0): CS goes LOW and selects the BME280.

Byte 1: the microcontroller sends 0xD0, the ID register (bit 7 = read). The reply is ignored.

Byte 2: the microcontroller sends a dummy 0x00. Its 8 clocks shift 0x60 back on CIPO.

cs(1): done. No ACK, so no scan(): reading a known ID register is SPI's scan().

COPI/CIPO: MOSI/MISO on many boards · machine.SPI · BME280 datasheet

I²C: reading the chip ID, bit by bit

SCL is the clock, SDA the data, both shared. The microcontroller (MCU) reads the chip ID:

i2c.readfrom_mem(0x76, 0xD0, 1) → b'\x60'

S start · W write · R read · A✓ ACK · Sr repeated start · N NACK · P stop

I²C: resistors pull HIGH, chips pull LOW

  • Pull-up resistors hold SDA (data) and SCL (clock) HIGH, at 3.3 V.
  • The microcontroller and the I²C device pull the lines LOW to communicate.
  • Some breakouts/modules bring their own resistors.
  • Pull too strong (low resistance), under ~1 kΩ at 3.3 V: chips can't pull LOW. Disable pull-ups on some boards.
  • Pull too weak (or long wires): signal takes too long to rise to 3V3. Reduce total resistance, or reduce bus frequency.

Reset the board mid-read and the sensor can keep holding SDA LOW, still waiting to finish its byte.

scan() fails until you unplug it.

Fix: drive GPIO to pulse SCL up to nine times, until SDA goes HIGH, then start I²C again. Or power-cycle the sensor.

Debugging

Same skillset in a different domain.

New sensor ready to go, but...

...but nothing happens, not even an error. Could it be the...

  • Code? the wrong pins, the wrong config, the wrong constructor?
  • Driver? the wrong defaults, similar but different chip, incomplete implementation?
  • Wiring? signals swapped, a loose jumper, a bad breadboard or solder joint?
  • Power? no power to the sensor, wrong voltage, grounds aren't joined?
  • Part? is it dead, a different version, or a known chip bug (errata)?

 Where do we start?

Stop guessing, start debugging

  1. Look first: Disconnect power, inspect for damage, heat, a burnt smell? Check cables
  2. Check power: Measuring voltage & ground, check signal directions and pins.
  3. Make it fail: the smallest test that consistently reproduces the issue.
  4. Change one thing at a time: and write down what you changed.
    "Remember kids, the only difference between screwing around and science is writing it down." Adam Savage, MythBusters
  5. Get a fresh view: explain it, or ask online/ai. Include code, wiring & the error.

Check power & cables

  • Cables: Some USB cable only charge. Use a known‑good data cable.
  • Battery banks: Some switch off when the board draws too little current.
  • Voltage: Ensure the right voltage level is used for your device and any components.
  • Ground: Has to be shared by every board and supply. Breadboard rails can be split.
  • Under load: Resets when a motor or Wi-Fi starts? A brownout. A meter misses it.

Wiring: look, wiggle, slow down, swap

Fine sometimes, and flaky others? Maybe something moved.

A good solder joint is smooth and concave. Lumpy or grainy may not connect at all. Headers must be soldered, not just pushed in.

Press on wires and parts as it runs. Comes and goes as you move? A connection. Changes with just a hand nearby? A floating input: add Pin.PULL_UP/DOWN.

Lower the bus speed, I2C(0, freq=100000), or the baud rate. Works now? Suspect the wires or pull-ups, not your code.

Another wire, another sensor, another board. A part you know works tells you which half is broken.

Why did it reset?

machine.reset_cause() says why the board last started. Ask first thing in main.py.

  • PWRON_RESETpower came on: plugged in, or the supply dipped (a brownout)
  • HARD_RESETthe reset button, machine.reset(), or a crash in C
  • WDT_RESETthe watchdog: your code hung and stopped feeding it
  • DEEPSLEEP_RESETit woke from machine.deepsleep()
  • SOFT_RESETCtrl-D or your editor restarted MicroPython, not the chip

Not every board tells them all apart: what it can't, it reports as one of the others.

    handler.stream.flush()               # or lost on a reset

REPL as a makeshift breakpoint

Wait in your main.py with an infinite loop + Ctrl-C: globals stay at the REPL.


# main.py
debug = {}               # global: kept
def main():
    while True:
        reading = sensor.read()  # local: lost
        debug['reading'] = reading  # copy it
        time.sleep(1)
main()                   # Ctrl-C any time

  • You can look, and manually execute code, but not step through.

Debug probe

  • Gives you a serial console on the board's UART pins, and SWD: the chip's own debug port.
  • Use it for: flashing or rescuing a board without its boot button, and logs when USB is busy.

Raspberry Pi Debug Probe: cables and a case included. For the Pico and other Arm boards at 3.3 V.

The probe and your Python

  • A console: bridges UART from the board to a different USB port. MicroPython can copy its REPL there.
  • Flashing: SWD writes new firmware with no button to press.
  • Debugging means the C firmware running the Python code, not your .py.

Multimeter

  • Shows volts, ohms and amps, and a beep when two points connect.
  • Use it for: checking power, a wire that isn't connected, a short.

Aneng AN8008 or similar: auto-ranging, with a continuity beep. For low-voltage electronics, not mains.

Mark Hennessy: budget multimeters, reviewed

Multimeter: three checks and a trap

  1. Voltage, power on: black on GND, red on 3V3. Expect 3.3 V.
  2. Continuity, power off: a beep means connected. 3V3 to GND must not beep.
  3. Current: the meter goes in the circuit, red lead in the mA jack.

Measure a voltage with the red lead still in the mA jack, and the meter shorts the supply and blows its internal fuse. Current reads 0.00 from then on.
Move it back to V.

USB power meter

  • Shows the volts and amps going into your board over USB, as it runs.
  • Use it for: resets when a motor starts, flat batteries, your power budget and calculate battery life.

RD TC66C or any meter that reads to 0.1 mA. It plugs in between the computer and the cable.

What a USB meter misses

  • Short spikes: it reads a few times a second, so a spike can fall between readings.
  • Sleep current: microamps, too small for most USB meters. That's a power profiler's job, such as Nordic's PPK2.
  • On USB, CircuitPython only pretends to sleep. Measure deep sleep on a battery.

Logic analyser: a real view into the signals

  • Shows the 0s and 1s on the bus signals, decodes the data of I²C, UART, SPI, and more.
  • Use it for: did the sensor answer? What did your code send?

Logic analyser: getting started

  • GND first, then a channel per signal: SDA, SCL.
  • Sample at least 4× faster than the signal: 24 MHz is plenty for I²C and UART.
  • Add a decoder for I²C, UART or SPI. PulseView's are written in Python.
  • A bare Pico is 3.3 V only; the €10 analyser copes with 5 V too.
