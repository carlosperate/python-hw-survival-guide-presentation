The same blink in each Python, each written the way its own docs teach it. MicroPython on the Pyboard D: the pyboard tutorial's loop, pyb.LED(n).toggle() and pyb.delay() (docs.micropython.org, pyboard/tutorial/leds); LED(2) is green on the D-series (pybd.io: 1 red, 2 green, 3 blue). Not machine.Pin here: the Pyboard D's LEDs are active-low (MICROPY_HW_LED_INVERTED in ports/stm32/boards/PYBD_SF2), so Pin.on() would turn one off, and Pin.toggle() isn't available on the stm32 port. CircuitPython on the Feather RP2040: Adafruit's blink template, "the CircuitPython 'Hello, World!'" (Adafruit_Learning_System_Guides, CircuitPython_Templates/blink), less its docstring and the blank line before the loop. direction and value are how Adafruit teaches it; switch_to_output() also works. No toggle method, so it sets value True and False. board.LED is GPIO13. CPython on the Pi 5: gpiozero's first recipe (gpiozero.readthedocs.io, recipes, LED), comes with Raspberry Pi OS; LED(17) is an LED wired to GPIO17. The recipe's alternative is led.blink() and signal.pause(). Blinka would run the CircuitPython version on the Pi too. MicroPython and CircuitPython

MicroPython

A lean Python 3 for microcontrollers, by Damien George.

The best of each chip. machine is the portable core, and each port adds modules for what only its chip can do.

CircuitPython

Adafruit's fork of MicroPython, for beginners and education.

The same code everywhere. One API on every board; a board that can't support a module leaves it out.

Blinka brings that API and Adafruit's drivers to CPython on a Raspberry Pi.

Sources: MicroPython libraries · CircuitPython core modules

Vertical slide: read on its own, skipped live. MicroPython: "a lean and efficient implementation of the Python 3 programming language that includes a small subset of the Python standard library" (micropython.org); aims at Python 3.4 with selected later features. Damien George, Kickstarter 2013, first release 3 May 2014. MIT licence. Its priority, from the library docs: port-specific libraries expose "hardware functionality unique to that platform. To write portable code use functions and classes from the machine module." Even machine varies by port: Pin ids "are port-specific", and "Not all ports implement" open-drain. CircuitPython: "a beginner friendly, open source version of Python for tiny, inexpensive computers called microcontrollers" (README); a fork of MicroPython, 1.0.0 announced 19 July 2017. MIT licence. Its priority, from the core modules page: "These core modules are intended on being consistent across ports and boards. A module may not exist on a port/board if no underlying hardware support is present", e.g. no analogio without analog hardware. Chip extras live in separate modules (rp2pio, espidf, espnow). It keeps merging MicroPython: the 10.4.0 alpha notes list "Merge from MicroPython v1.28 and v1.29". Blinka: "Add CircuitPython hardware API and libraries to MicroPython & CPython devices" (github.com/adafruit/Adafruit_Blinka); also Jetson boards.

Vertical slide: read on its own, skipped live. Hardware: CircuitPython README, "Unified hardware APIs", "No machine API"; MicroPython machine docs, plus port modules such as rp2, esp32 and pyb. Pins: machine.Pin ids "are port-specific", "an integer, a string or a tuple"; rp2 accepts names like "GP15" and "LED". CircuitPython's board module holds "board base pin names" that "vary from board to board", named as printed on the board; board.I2C() returns the board's designated I2C bus. Not on the slide, same idea: CircuitPython's os, time and random are strict subsets of CPython's, "tick count is available as time.monotonic()", so its code "is runnable on CPython but not necessarily the reverse" (README). MicroPython's time has its own ticks_ms() and ticks_diff(), and no monotonic(). Concurrency: README, "Interrupts and threading are disabled"; FAQ, "please use asyncio for multitasking", asyncio since 7.1.0. MicroPython: Pin.irq, machine.Timer, _thread only on some ports (rp2, esp32, unix). Workflow: README, native USB on most boards, BLE otherwise; ESP32 and ESP32-C3 use the Wi-Fi workflow. MicroPython's pyboard is the exception that also shows up as a USB drive. Files: "CircuitPython cannot write to the filesystem at the same time as your computer"; boot.py can call storage.remount() to give the code write access instead (CircuitPython Essentials, Storage). Libraries: mip installs from micropython-lib, GitHub, GitLab or a URL, not PyPI; circup updates libraries from the Adafruit and Community bundles; "300+ device libraries and drivers" (README).

Vertical slide: read on its own, skipped live. On a laptop, Python is a guest of the operating system: processes, virtual memory, a filesystem, a package manager, a debugger. On a microcontroller the interpreter effectively is the OS: one program, no process isolation, no swap. mip installs precompiled .mpy packages from micropython-lib, not PyPI. The filesystem lives in the chip's flash: on a 2 MB Pico the rp2 port gives it 1,408 KB by default. The REPL comes over USB serial. Resets are part of normal operation: when it crashes, nothing catches you; the chip restarts.

Sources: MicroPython reset and boot · CircuitPython README

Vertical slide: read on its own, skipped live. MicroPython (docs, reset_boot): the frozen _boot.py runs first and formats the filesystem on first boot; boot.py should "always exit and not run indefinitely"; main.py may loop; the REPL starts if main.py is missing or exits, and "Any global variables that were set in boot.py and main.py will still be set in the global context of the REPL". Ctrl-D or machine.soft_reset() "clears the Python interpreter, frees all Python memory", then boot.py and main.py run again. Hard reset: power-up, reset button, machine.reset(), deep-sleep wake, watchdog, brown-out. Recovery: Ctrl-C, then os.remove('main.py'); safe mode on some ports; a factory reset erases the filesystem. This is the beginner "soft brick": main.py loops forever and you can't get the REPL back. Foreshadows the defensive main.py in Debugging. CircuitPython (README, Behavior): boot.py "runs only once on start up before workflows are initialized", output in boot_out.txt; code.py "is run after every reload", then "the vm and hardware is reinitialized", so "the REPL is a fresh vm"; a write to the drive reruns code.py. Safe mode "does not run user code after a hard crash or brown out"; pressing reset in the 1 s boot window also enters it. Status LED as on the slide.

Three things you just lost

No OS

A micro:bit V2 has 128 KB of RAM. Total.

No safety net

5 V on a 3.3 V pin is out of spec. Interrupt handlers can't allocate.

No familiar tools

No step debugger in the firmware you flashed.

micro:bit V2: 128 KB RAM (tech.microbit.org). RP2040 absolute maximum IO voltage is IOVDD + 0.5 V, 3.8 V on a 3.3 V Pico (RP2040 datasheet 5.5). A hard ISR cannot allocate (MicroPython ISR rules). sys.settrace "is typically not present in pre-built firmware" (sys docs).
