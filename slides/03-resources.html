What changes when the same Python runs on a microcontroller; the rest of the part takes these one at a time. RAM: the square is 16 GB of laptop RAM, the small one 16 MB of PSRAM at true area, 1/32 of the side (16 GiB / 16 MiB = 1,024, derived). 16 MB is the top end: Espressif's ESP32-S3-DevKitC-1-N32R16V, whose ESP32-S3-WROOM-2 module has 32 MB of Octal flash and 16 MB of Octal PSRAM at 1.8 V (esp-dev-kits user guide). MicroPython runs it with the ESP32_GENERIC_S3 SPIRAM_OCT firmware, and CircuitPython has a build for it. The photo is the same board with the WROOM-1 module (Espressif, Apache 2.0). 8 MB is common on ESP32-S3 boards (N8R8, Arduino Nano ESP32). Next click zooms into the 16 MB square and lines up popular boards at the same scale: micro:bit V2 128 KB (nRF52833), Feather RP2040 264 KB (RP2040), Pico 2 520 KB (RP2350), Arduino Nano ESP32 8 MB of PSRAM beside its 512 KB of SRAM (NORA-W106-10B, Arduino's cheat sheet; MicroPython's ARDUINO_NANO_ESP32 build, and CircuitPython has one too). Each side is 300 px × √(RAM / 16 MB), computed. Python gets less than the chip's RAM: the firmware takes its share. No swap: one fixed heap (constrained.html, "a fixed size pool known as the heap"). Compiled on the board: "When a module is imported, MicroPython compiles the code to bytecode", stored in RAM (constrained.html). Collecting costs time: "A GC can take several milliseconds" (constrained.html). Speed: "naive Python code roughly 100x slower than C" (Damien George, PyCon AU 2018, summary slide).

Symptom first. Next: where the memory goes (your code, then single lines), then the fixes. What MemoryError means: an allocation looks for a run of free blocks; if there is none it collects and tries again, and only then raises "memory allocation failed, allocating N bytes" (py/gc.c gc_alloc, py/runtime.c). At import: a .py is compiled on the board, so a module "will consume RAM at the time of import" (constrained.html). In Discussion #12564 a 2,000-line program hit MemoryError at import with ~158 KB free, and removing 30 comment lines fixed it. One big thing: micropython-lib requests' .json() reads the whole body, then parses it (json.loads(self.content) in requests/__init__.py). After hours: a list that grows forever, or fragmentation; the collector never compacts (constrained.html). Press down: reading mem_info.

* Peak and ends measured on the unix port

A .py is compiled on the board: parsing builds a tree of the whole module, compiling turns it into bytecode, then the tree is freed. "The bytecode is stored in RAM. The compiler itself requires RAM, but this becomes available for use when the compilation has completed" (constrained.html). Damien George, PyCon AU 2018: the compiler "can leave memory fragmented from parse tree", and "all identifiers are left interned/stored in RAM". Measured on MicroPython's unix port (v1.30.0-preview, b70ae1a, 64-bit), importing robert-hh's bme280_float.py (10,022 bytes; 2,809 as .mpy). Peak is mem_peak() over the start of the import, "stays" is gc.mem_alloc() after a collect: .py 29,115 / 6,656 bytes; .mpy 6,845 / 6,464; ROMFS 4,250 / 4,160; frozen 2,398 / 1,248. The curves between those points are illustrative. A 32-bit board uses fewer bytes; measure yours with gc.collect(); gc.mem_free() before and after the import. The 20 KB ceiling is a what-if. A real case: a 2,000-line program on an RP2040 hit MemoryError at import with ~158 KB free, and removing 30 comment lines fixed it (Discussion #12564). .mpy skips the compiler, but its bytecode still loads into RAM (Discussion #12564). ROMFS (v1.25, mpremote romfs deploy) runs .mpy in place from flash with no firmware rebuild, but it isn't in the default Pico or ESP32 builds (rp2's MICROPY_HW_ROMFS_BYTES defaults to 0): check mpremote romfs query. Frozen modules keep bytecode, names and constants in flash (manifest.html). CircuitPython's library bundle is already .mpy. Import order: RAM taken at import "is then unavailable for the compiler to use on subsequent imports" (constrained.html), and "the memory gets fragmented differently depending on allocation order" (CircuitPython FAQ). Selective imports: "does NOT reduce your memory usage" (Adafruit, Memory-saving tips for CircuitPython).

Which lines cost memory?

  • if, for, while, try
  • locals, small-int maths: n += 1
  • calling a function or a method
  • reading a pin: pin.value()
  • writing into a buffer: buf[i] = b
  • import, def, class
  • a new list, dict, str or bytes
  • s + t, f"{t}", data[4:20]
  • uart.read(64)
  • float maths, even n / 2*

Control flow is free. Each new object takes at least one 16-byte block.

After Damien George, PyCon AU 2018 · *MicroPython only

Most of your Python is fine: memory goes on new objects, not on logic. Damien George's PyCon AU 2018 slides, "Memory allocation": expressions, if/while/for/try, local variables, small integer arithmetic, in-place operations on existing data structures, calling functions/methods with positional or keyword args and builtins like len, min, max, sum, print don't allocate. Importing, defining functions and classes, assigning a global for the first time and creating data structures do. Every line on this slide was run under micropython.heap_lock() on the unix port (v1.30.0-preview, b70ae1a): the results match. Reading a pin or ticks_ms() returns a small int, so nothing is allocated. Floats: on MicroPython's default object representation (rp2, esp32, stm32, nrf) every float result is a new heap object, and n / 2 is a float even when n is an int: use n // 2. CircuitPython packs 30-bit floats into the object word (MICROPY_OBJ_REPR_C in circuitpy_mpconfig.h), so its float maths doesn't allocate; MicroPython does the same only on esp8266 and a few Arduino and OpenMV boards. One block is 16 bytes on 32-bit (develop/memorymgt); the allocator rounds every request up to whole blocks (py/mpconfig.h). Computed, not measured. Press down for the longer, tested list.

MicroPython unix port, v1.30.0-preview (master b70ae1a, 2026-10-19), 64-bit. Its small ints go to ±2^62, so the ±2^30 limit for 32-bit boards is from isr_rules.html ("Values between 2**30 -1 and -2**30 will be stored in a single machine word"). Surprises: obj.m() is free but cb = obj.m makes a bound method, which is why ISR code binds it once in __init__ (isr_rules.html); for i in range(n) is free, but enumerate() and zip() create an iterator object; reading a float out of an array('f') makes a float. Slice assignment into a bytearray or memoryview is free since v1.26. Not on the slide: raising an exception allocates (96–128 bytes here), but under heap_lock MicroPython falls back to a static exception, so the test can't catch it. A function needing more than 11 words of frame takes it from the heap and frees it on return (py/objfun.c).

packet[4:20]→a memoryview: no copy

magic numbers as globals→const()
allocating in a hard ISR (Interrupt Service Routine)→micropython.schedule()
r.json() on a big reply→json.load(r.raw): parsed as it arrives

    events.append(pin.value())         # ✕ heap locked, MemoryError when list grows
    micropython.schedule(record, pin)  # ✓ record() runs soon, and may allocate

Most of your Python habits are fine; this matters in hot loops, interrupt handlers and big data. Each line was tested under heap_lock() on the unix port, as for "Which lines cost memory?". s += copies the whole string each time; join builds it once, or write into a bytearray through a memoryview (constrained.html). readinto() fills the buffer you made once (speed_python.html). A memoryview is a small fixed-size object, so a view costs one block whatever its size (speed_python.html). Floats: each result is a new heap object on MicroPython's default ports, and / makes a float even from ints; 65535 × 3300 is under 2^30, so the int stays small (computed). CircuitPython's 30-bit floats live in the object word (circuitpy_mpconfig.h). const(): a name with a leading underscore isn't stored in the module dict at all (micropython module docs, constrained.html). Hard ISRs run with the heap locked: "memory allocation failed, heap is locked"; schedule() runs the callback "very soon" when the heap isn't locked (isr_rules.html). CircuitPython has no user interrupt handlers. Big data: micropython-lib requests' .json() is json.loads(self.content), so the whole body sits in RAM before parsing; r.raw is the body stream. MicroPython's json.load reads its stream one byte at a time (extmod/modjson.c), so only the parsed result is kept. CircuitPython's adafruit_requests already does json.load(self.raw) in .json(). Floats: ~20 KB vs ~4 KB is computed for 32-bit ports with heap floats (4 B pointer + 16 B float each, vs 4 B per element). Measured on the unix port (64-bit): 40,224 bytes for the list, 4,064 for the array. On CircuitPython floats live in the list slot, so the list is ~4 KB too. Also worth knowing, if asked: build a web page piece by piece instead of one string (constrained.html), CircuitPython's OnDiskBitmap draws from flash instead of loading the image (Adafruit memory-saving tips), and if it is still too big, ask the API for less or use a board with PSRAM.

A big object needs one hole that big.

The one mechanism slide: keep it under a minute. Illustrative: a toy heap of 27 blocks, first fit, collected only when an allocation fails (py/gc.c gc_alloc), the way MicroPython does it. Block size: MICROPY_BYTES_PER_GC_BLOCK is 4 words (py/mpconfig.h), so 16 bytes on a 32-bit board and 32 on a 64-bit one such as the unix port; no board port overrides it. Every allocation is rounded up to whole blocks. Each reading keeps a float (one block) and makes a string (two blocks: the object and its text); the string is garbage once msg points at the next one, but nothing frees it until a collection. bytearray(64) needs its 64 bytes as 4 blocks in a row; its 16-byte header is one more block, which fits in any hole, so only the data is drawn. The collection frees 8 strings (the last is still msg), leaving 16 free blocks, 256 bytes, but no two holes touch: the largest is 32 bytes. The collector never moves objects, so "despite there being a substantial amount of RAM available, there is insufficient contiguous space" (constrained.html). Real case: a user reported 14,768 bytes free, max free sz: 135 (blocks, so 2,160 bytes), and a 4,033-byte allocation failing (MicroPython forum p=28215, now 404: say "a user reported").

The newest pushes the oldest out.

A leak: nothing is wrong with the heap; the program keeps a reference to everything it ever read, so each collection frees less, until one allocation fails. The strip is illustrative, one block per reading. Usual suspects: a list of readings, a log string, a cache dict, callbacks registered again on every reconnect. MicroPython's deque needs maxlen ("maxlen must be specified"); when full, new items discard items from the other end, or pass flags=1 to raise IndexError instead (collections docs). In CircuitPython deque is on full builds only. Other bounds: an array used as a ring buffer, running min/max/mean instead of every sample, write to flash in batches.

Make the hot loop fast


def checksum(buf):
    s = 0
    for b in buf:
        s += b
    return s & 0xFFFF
      

@micropython.native
def checksum(buf):
    s = 0
    for b in buf:
        s += b
    return s & 0xFFFF
      

@micropython.viper
def checksum(buf) -> int:
    p = ptr8(buf)
    s = 0
    for i in range(int(len(buf))):
        s += p[i]
    return s & 0xFFFF

Fixed-point Mandelbrot, Metro RP2040 · Adafruit

  • nativeyour Python, compiled to machine code instead of bytecode
  • viperalso raw ints and pointers: no floats, no overflow checks
  • Turbonative & viper on CircuitPython, pre-built on your computer
Measure first: time.ticks_us() around the loop. Then make that one function faster; the rest of the program stays plain Python. @micropython.native compiles the same Python to machine code, "roughly twice the performance of bytecode". @micropython.viper goes further for "integer arithmetic and bit manipulation": typed locals, ptr8/ptr16/ptr32 for buffers, and no overflow checks (speed_python.html, "The Viper code emitter"). Both compile here with mpy-cross -march=armv6m. The bars are Adafruit's measurement, not this checksum: a fixed-point Mandelbrot, 160 × 120, up to 64 iterations, median times on a Metro RP2040 with CircuitPython 10.3.0-42-g3cdb20693f, recorded 8 September 2026: bytecode 8,335.3 ms, native 4,778.0 ms (1.74×), viper 422.9 ms (19.71×) (CircuitPython Turbo guide, "Measured speed"). The speed-up is for that function, not the whole program. Turbo is not a new mode: it is the same native and viper emitters, reached another way. CircuitPython builds leave the on-board native emitter out (CIRCUITPY_ENABLE_MPY_NATIVE ?= 0, "experimental", circuitpy_mpconfig.mk), so @micropython.native and viper don't compile on the board. The raspberrypi port does load native .mpy files (CIRCUITPY_LOAD_NATIVE ?= 1). Turbo uses that: mpy-cross on your computer compiles the one function for the board's CPU into a .mpy, and a small shim falls back to the Python source when no matching .mpy is installed. RP2040 and RP2350, latest builds (Turbo guide, "How Turbo works"; Electronics For You, 15 September 2026). "Viper: no floats" and the wrap-around rule are from Adafruit's PixelDust guide and speed_python.html. Other speed habits (Damien George, PyCon AU 2018): use locals, cache methods in locals, const(), and built-ins.

Measure first. Allocate once. Stream the rest.

Watch: Adafruit's first tip is to measure, gc.collect() then gc.mem_free() before and after each section, imports included. Schedule: automatic collections run when an allocation fails, so they land wherever you happen to be. A user's 120 Hz callback was delayed every 1.3 s by them (MicroPython Discussion #19676, 2026); collecting on their own schedule stopped the lost callbacks. A collection is "about 1ms on the Pyboard" when done frequently (constrained.html), but a measurement in the same thread found the pause depends mostly on how much live data there is to scan: time it with ticks_us on your board. gc.threshold(gc.mem_free() // 4 + gc.mem_alloc()) collects after a quarter of the free heap is used. Prove: heap_lock() makes any allocation raise MemoryError (micropython module docs); CircuitPython leaves it out. Hard ISRs already run with the heap locked: "memory allocation failed, heap is locked". Recover: the defensive main.py in Debugging, catching MemoryError. By the time the handler runs, the failed call's objects are unreachable, so logging usually finds room; the reset gives a heap with no holes. Each bullet's code shows on the right, one at a time.
